# Quickstart: Collaborative Undo / Redo

**Feature**: `006-undo-redo`
**Date**: 2026-05-20

---

## Prerequisites

- Node.js 20+
- Workspace dependencies installed: run `npm install` from the repo root (installs all workspaces).
- Familiarity with the existing draw pipeline (`useCanvas`, `useCanvasRenderer`, `eventHandlers.js`).

---

## Running the Application

```bash
# Start both server and client in separate terminals

# Terminal 1 — server (port 3001)
cd server && npm run dev

# Terminal 2 — client (port 5173)
cd client && npm run dev
```

Navigate to `http://localhost:5173`, create or join a room, and open a second tab/browser to test collaborative undo/redo.

## Manual Test Scenarios

### Scenario 1: Undo your own stroke

1. Draw several strokes on the canvas.
2. Press **Ctrl+Z** (or Cmd+Z on macOS) — most recent stroke disappears on both tabs.
3. Repeat to undo further strokes.
4. When all your strokes are undone, the Undo button becomes disabled.

### Scenario 2: Redo an undone stroke

1. Draw a stroke, then undo it (Ctrl+Z).
2. Press **Ctrl+Y** (or Cmd+Y) — the stroke reappears.
3. Draw a new stroke after undoing — Redo becomes disabled.

### Scenario 3: Any user undoes a clear

1. Tab A draws several strokes.
2. Tab B clears the canvas.
3. Tab A (or Tab C if open) presses **Ctrl+Z** — all pre-clear strokes are restored on every tab.
4. Verify no redo is available for the clear.

### Scenario 4: Toolbar button states

1. Open the app with no strokes drawn — both Undo and Redo buttons should be disabled.
2. Draw a stroke — Undo becomes enabled, Redo remains disabled.
3. Undo the stroke — Undo becomes disabled (if no more history), Redo becomes enabled.
4. Click Redo — both buttons return to their previous state.

## Architecture Decision Summary

- **Server-authoritative**: All undo/redo history lives on the server. Clients emit requests and apply only what the server broadcasts back. No optimistic rendering.
- **Personal + shared clear**: Each user's personal undo stack covers their DRAW/ERASE (and CLEAR they triggered). The room's `latestClearEntry` is a shared resource — any user can consume it once.
- **Reverse-chronological ordering**: When both a personal op and the room clear are undoable, the server picks the one with the higher timestamp (FR-002).
- **No redo for clear**: Once a clear is undone it is consumed and never placed on any redo stack (FR-005).
- **Timeout guard**: Client disables the button while awaiting confirmation; re-enables after 5 seconds if the server does not respond (FR-014).
